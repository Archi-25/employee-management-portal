1. The dictionary

Every word this project uses, explained once, properly. Read it top to bottom. It will feel like a lot — but each entry is three sentences, and you will meet all of them again later.

1.1 Basic web words

HTML — the language that describes what is on a page: a heading, a paragraph, a button. It is a list of nested tags like <button>Save</button>. Think of it as the skeleton.
CSS — the language that describes how the page looks: colours, spacing, size, fonts. Think of it as the clothes on the skeleton.
JavaScript — the language that describes what the page does when you interact with it: what happens when you click, type, or scroll. Think of it as the muscles.
DOM (Document Object Model) — the live, in-memory version of the page that the browser actually keeps while the page is open. When we say "put it in the DOM", we mean "make it really appear on screen". When we say "removed from the DOM", the element does not exist at all — it is not merely hidden.
Browser — Chrome, Safari, Firefox. It downloads your files, builds the DOM, and runs your JavaScript.
Server — another computer, somewhere else, that sends the browser its files and data. In this project the "server" is faked (explained later), but the code is written exactly as if it were real.
API (Application Programming Interface) — the set of web addresses the server offers for data, for example /api/employees. The browser asks those addresses for data instead of asking for a whole page.
URL / route — the address in the browser bar, e.g. /employees/7/edit. In this app, the part after the domain decides which screen you see. A route is one rule that maps one URL pattern to one screen.
localStorage — a small notepad the browser keeps on your own computer, per website. Anything you write there survives closing the tab. This app uses it to remember who is signed in and which theme you chose.
JSON — a plain-text way of writing data that looks like JavaScript objects: {"name": "Mei", "age": 30}. It is how data travels between browser and server.

1.2 TypeScript words

TypeScript — JavaScript with types added. You write TypeScript; a tool converts ("compiles") it into plain JavaScript that browsers understand. The whole point is that mistakes are caught while you type instead of when a user clicks.
Type — a label saying what kind of value something is: string (text), number, boolean (true/false). If you promise a number and hand over text, the compiler stops you.
interface — a description of the shape of an object: which fields it must have and of what type. It is a contract only; it disappears completely when the code is compiled. Example from this project: 
interface Address {
  line1: string;
  city: string;
  state: string;
  pincode: string;
}
Now anything typed Address must have exactly those four text fields.
type alias (the type keyword) — a nickname for a type. It can also list the only allowed values, which is how this project defines roles: 
type Role = 'GUEST' | 'EMPLOYEE' | 'MANAGER' | 'ADMIN';
The | means "or". A Role can only ever be one of those four exact strings. Typing 'ADMINN' becomes an error before the app ever runs.
class — a blueprint that bundles data and the functions that work on it. Every screen in this project is a class.
readonly — "this can be set once and never changed afterwards". A safety label.
private / protected / public — who is allowed to touch a field. private = only this class. protected = this class and its HTML template. public (the default) = anyone. This project uses protected for anything the template needs and private for everything else.
Omit<A, 'b'> — a built-in helper meaning "the type A, but without field b". This project writes type EmployeeDraft = Omit<Employee, 'id'>, which means "an employee that does not have an id yet" — exactly what you have before saving a new person, because the id is assigned by the server.
Partial<A> — "the type A, but every field is optional". Used when you are updating only some fields.
Record<K, V> — "an object whose keys are of type K and whose values are of type V". Record<Role, number> means an object with one number for each role.
Generic (the <T> brackets) — a type with a blank to be filled in later. Page<Employee> means "a Page of Employees"; Page<Announcement> means "a Page of Announcements". One definition, many uses.
?. (optional chaining) — "read this, but if the thing on the left is missing, just give me nothing instead of crashing". employee?.name is safe even when employee is null.
?? (nullish coalescing) — "use the left value, unless it is missing, in which case use the right one". name ?? 'Guest'.
... (spread) — "copy everything out of this". { ...person, city: 'Pune' } means "a new object with all of person's fields, except city is now Pune". The original is untouched — this is how the project changes data without editing it in place.
async / await / Promise — a Promise is a receipt for a value that will exist later (for example, data still travelling from the server). await means "pause here until the receipt is honoured", and a function containing await must be marked async. It lets slow code be written in a straight line.
Arrow function — a short way to write a function: (x) => x * 2 is a function that doubles its input.

1.3 Angular words

Angular — the framework this project is built with. A framework is a large pre-written toolkit that gives you structure: how to split a page into pieces, how to fetch data, how to move between screens. You write your parts; Angular runs them.
Component — the basic building block. One component = one piece of screen. It has three parts: a template (its HTML), styles (its CSS), and a class (its TypeScript logic and data). A page is components inside components inside components.
Template — a component's HTML, with extra Angular syntax mixed in so it can show live data.
Decorator — a line beginning with @ written directly above a class, which tells Angular what the class is. @Component says "this is a screen piece", @Injectable says "this is a shared worker", @Directive says "this adds behaviour to an element". Think of it as a label on a box.
selector — the HTML tag name you use to place a component. If a component declares selector: 'app-card', you drop it into any template by writing <app-card></app-card>.
Standalone component — a component that lists its own dependencies in an imports array, instead of being registered in a big shared list called an NgModule. Everything in this project is standalone except the admin area, which deliberately uses the old NgModule style to show both approaches.
Interpolation — the {{ }} syntax. {{ name }} in a template means "print the current value of name here". It updates automatically when the value changes.
Property binding — square brackets: [value]="total". It means "keep this element's value property equal to my total variable". Data flows from the class into the HTML.
Event binding — round brackets: (click)="save()". It means "when this is clicked, run my save function". Data flows from the HTML back into the class. A memory trick: [square] goes in, (round) comes out.
@if / @for — Angular's built-in template blocks. @if (x) { ... } shows the contents only when x is true. @for (item of list; track item.id) { ... } repeats the contents once per item. track tells Angular how to recognise each row so it can move existing rows instead of rebuilding the whole list.
Directive — extra behaviour attached to an element that already exists, rather than a new element of its own. Two kinds: attribute directives change how an element looks or behaves (a tooltip); structural directives add or remove elements from the DOM entirely (show this button only for admins). Structural ones are written with a leading *.
Pipe — a small formatter used inside a template with the | symbol. {{ salary | currency }} takes the raw number and prints it as money. Pipes only change what is displayed; the underlying data is untouched.
Service — a plain class that does work but owns no screen: fetching data, keeping the session, writing logs. Components stay small by handing jobs to services.
Dependency Injection (DI) — the system that hands a component the services it needs, instead of the component building them itself. You write private auth = inject(AuthService), which means "Angular, give me the AuthService". Angular creates one and keeps reusing the same one.
In plain terms: you do not go to the kitchen and cook; you ask for the dish and it arrives. And because everyone asks the same kitchen, everyone gets the same food — which is exactly why signing in on one screen is instantly known by every other screen.
Provider — the recipe that tells DI how to make something. useClass = build this class. useValue = just use this fixed value. useFactory = run this function to build it. useExisting = do not build anything, point at a thing that already exists.
Injectable / providedIn: 'root' — the label on a service saying "DI may create me, and there should be exactly one of me for the whole application". One shared copy is called a singleton.
InjectionToken — a unique name-tag used to inject something that is not a class (a settings object, a list of flags). You cannot write inject(SomeInterface) because interfaces vanish at compile time, so you make a token instead and inject that.
Router — the part of Angular that watches the URL and swaps the right screen into the page, without ever reloading the browser. That is what makes it a single-page application: one page load, many screens.
router-outlet — the placeholder tag in a template that says "whichever screen the URL selects, render it right here".
Lazy loading — not downloading a screen's code until someone actually visits it. Written as loadComponent: () => import('...'). It makes the first page load much faster, because the admin area (which most people never open) is never sent to most people.
Guard — a function that runs before a route is allowed, and answers yes or no. Returning true lets the navigation through; returning a redirect sends the user somewhere else. This is how "you must sign in first" is enforced.
Resolver — a function that fetches data before a screen is shown, so the screen never has to render an empty state while waiting.
Lifecycle hook — a method Angular calls at a fixed moment in a component's life. ngOnDestroy() runs just before the component is removed — the place to clean up timers. ngAfterViewInit() runs once the component's HTML actually exists.
Change detection — Angular's process of checking "has any displayed value changed, and does the screen need updating?". OnPush is a setting meaning "only re-check me when something I actually depend on changes" — faster than checking everything constantly.
Zoneless — this app runs without Zone.js, the older library that detected changes by secretly wrapping every browser function. Instead, signals report their own changes. Less magic, less work, faster app.
SSR (Server-Side Rendering) — building the first version of the page on the server and sending finished HTML, so the user sees content immediately instead of a blank screen.
Hydration — what happens next: the Angular app starts up in the browser and "adopts" the HTML the server already sent, attaching the click handlers to it rather than throwing it away and rebuilding.
ViewEncapsulation — the rule about whether a component's CSS can escape. Emulated (the normal default) = my styles stay inside me. None = my styles leak into the whole page. ShadowDom = a sealed bubble; nothing gets in or out.
Content projection — letting a parent pass HTML into a child component, which the child places using <ng-content />. It is how one Card component can wrap any content at all.
Reactive forms — building a form in TypeScript (FormBuilder, FormGroup, FormControl) rather than in HTML, so the rules and the current values live in code where they can be tested.
Validator — a rule attached to a form field, e.g. Validators.required. A field that breaks a rule is invalid. touched means the user has visited and left it — the project only shows errors on touched fields, so you are not scolded before you type.
Sanitisation — Angular automatically stripping dangerous parts out of HTML that came from a user (scripts, onerror= handlers) before putting it on screen. It prevents an attack called XSS, where someone types code into a text box and it runs on other people's computers.

1.4 Signals and observables

These two are the heart of the project, so they get more space.

Signal — a box holding one value, which announces it when the value changes. You read it by calling it like a function: 
const count = signal(0);   // create a box holding 0
count();                   // read it  -> 0
count.set(5);              // put 5 in the box
count.update(n => n + 1);  // change it based on what is inside -> 6
In plain terms: a signal is a value that tells you when it changes. Any template that read it is redrawn automatically. This is why you will never see code in this project that says "now go update the screen" — the screen follows the data by itself.
Watch out: the brackets matter. count is the box; count() is what is inside it. Forgetting the brackets in a template prints something like "function count()" instead of a number.
computed — a signal calculated from other signals. It recalculates itself only when one of its ingredients changes, and caches the answer otherwise. 
const total = computed(() => employees().length);
You never set a computed value; you only ever read it. It is derived data, and it can never go stale or disagree with its source.
effect — a block of code that re-runs whenever any signal it reads changes. Used for side effects — things outside Angular, such as writing to localStorage or changing an attribute on the page. Rule of thumb: use computed to calculate, use effect to act.
asReadonly() — hands out a version of a signal that can be read but not changed. Services use it so that outsiders can watch the value while only the service itself may set it.
input() / output() — how components talk to each other. An input is data a parent passes down into a child. An output is an event a child sends up to its parent. input.required<Employee>() means "I must be given an employee; refuse to compile otherwise".
Observable — a stream of values arriving over time, rather than one value now. A signal is a box; an observable is a pipe. HTTP responses, timers and typing events are all observables. Nothing happens until someone subscribes — an unsubscribed observable is a tap nobody opened.
subscribe — "start listening to this stream, and here is what to do with each value". You may pass three named handlers, called an Observer: 
stream.subscribe({
  next:     (value) => { /* a value arrived */ },
  error:    (err)   => { /* it failed */ },
  complete: ()      => { /* it finished */ },
});
unsubscribe / teardown — stopping the listening. This matters: a timer that is never stopped keeps running after you leave the screen, quietly wasting battery forever. That mistake is called a memory leak, and this project takes deliberate care to avoid it.
RxJS — the library that provides observables and the operators below.
Operator — a small transformation applied to a stream inside .pipe(...). The ones used in this project:
OperatorWhat it does, in plain words
mapChange each value into something else. "Give me just the items array out of this response envelope."
filterLet only some values through. "Only even-numbered ticks."
tapPeek at a value without changing it — used for logging.
takeUntilKeep going until another stream fires, then stop. The standard way to end a subscription when a screen closes.
debounceTimeWait for a pause. "Only search once they have stopped typing for 250ms."
distinctUntilChangedIgnore a value identical to the previous one.
catchErrorHandle a failure in the stream.
finalizeRun this at the very end, whether it succeeded or failed — like a "finally" block.
shareReplayOne shared stream for many listeners, instead of restarting it per listener.
mergeMapFor each value, start another stream and merge the results in.
delayHold each value back for a while — used here to fake network slowness.
Subject — an observable you can push values into by hand. Used in this project as an on/off switch: a destroy$ Subject that fires once when a screen closes, which every takeUntil is watching.
firstValueFrom — converts an observable into a Promise by taking its first value. It lets the stores use easy await syntax over HTTP calls.

1.5 HTTP words

HTTP — the language browsers and servers speak. A request goes out, a response comes back.
HTTP methods — the verb of the request: GET = read something, POST = create something, PUT = update something, DELETE = remove something.
Status code — the three-digit result. 200 fine, 201 created, 204 done with nothing to return, 403 you are not allowed, 404 not found, 409 conflict, 500 the server broke.
Header — extra labelled information attached to a request, such as who you are. This project attaches Authorization and X-Portal-Role headers.
Token — a string that proves you are signed in, sent with every request so the server knows who is asking.
Interceptor — a function every HTTP request passes through on its way out and every response passes through on its way back. Interceptors are stacked, so a request travels down through all of them and the response travels back up.
In plain terms: think of airport checkpoints. Your request walks through check-in, security and the gate on the way out, and back through them in reverse on the way home. Each checkpoint can stamp it, time it, redirect it, or turn it back.
Cache — keeping a copy of an answer so the same question does not have to be asked twice. A TTL (time to live) is how long the copy stays trustworthy — 30 seconds here.

2. The big picture

What is this app?

It is an internal website for a company's HR department — the tool staff would open at work to look up colleagues and manage people. It has eight screens:

ScreenWhat you do there
LoginSign in. Three demo accounts let you try each role.
DashboardThe home page: headcount, attendance today, birthdays, announcements, recent activity.
EmployeesThe staff directory. Search, filter, sort, page through, view one person, add, edit, delete.
AttendanceWho was present, late or absent on a chosen day.
LeaveApply for holiday; managers approve or reject requests.
DepartmentsThe list of departments, with headcount, and a detail panel per department.
AdminFive sub-pages: overview, announcements, system health, audit log, settings.
SettingsYour own profile, theme choice, change password.

The four roles

Everything in the app is shaped by who you are. There are four roles, ranked:

GUEST (0)  <  EMPLOYEE (1)  <  MANAGER (2)  <  ADMIN (3)

Each role can do everything the ones below it can, plus more. Giving each role a number is what makes the check simple: "is my number at least as big as the number required?" That single comparison lives in AuthService.hasRole() and is used everywhere.

RoleCan do
GUESTSee the dashboard only. Not signed in.
EMPLOYEESee the directory, and their own attendance and leave. Apply for leave.
MANAGEREverything above, plus: see everyone's attendance and leave, approve/reject leave, add and edit employees, see salaries, reach the admin area.
ADMINEverything, plus: delete employees, manage departments, and open admin settings.
The most important idea in the whole project: the role is checked in three separate places — the route guard (can you open this URL?), the structural directive (does this button even exist in the page?), and the fake API (will the data layer obey this request?). Hiding a button is only politeness; the check on the data side is the real lock. Anyone can open the browser's developer tools and unhide a button, but they cannot talk the API into deleting a record their role is not allowed to delete.

The one rule about folders

Imports may only travel downwards:

features/   the screens
    |  may use
    v
shared/     reusable UI
    |  may use
    v
core/       data, services, no UI at all

So a screen may use a card; a card may use a service; but core may never import a button, and shared may never import a screen. Why does this matter? Because it means you can read core without knowing anything about the screens, and you can delete a screen without breaking anything below it. When two layers may call each other freely, you eventually cannot change either one safely — every file becomes tangled with every other file.

3. One click, start to finish

This is the section to understand properly. We will follow one action — an admin deleting an employee — through every layer of the app. Every file mentioned here is explained in full later; right now, just watch the journey.

Step 1 — The button exists at all

<button *appHasRole="'ADMIN'" (click)="askToDelete(employee)">Delete</button>

*appHasRole="'ADMIN'" is a structural directive. If you are not an admin, this button is not hidden with CSS — it is never created. It does not exist in the DOM. A manager inspecting the page with developer tools finds nothing to unhide.

Step 2 — The click is caught

(click)="askToDelete(employee)" runs a method on the EmployeeList class. That method does not delete anything. It stores the employee in a signal: 

this.pendingDelete.set(employee);

Because pendingDelete is a signal, and the template has @if (pendingDelete()) around a confirmation dialog, the dialog appears on screen by itself. Nobody wrote "now show the dialog" — the screen simply follows the data.

Step 3 — The user confirms

The dialog's Confirm button calls confirmDelete(), which clears the signal (dialog disappears) and calls the store: 

await this.store.remove(employee.id);

Step 4 — The store takes over

EmployeeStore is the app's memory for employees. Its remove method first records that something is in progress, then asks the service to do the work: 

patchState(store, { loading: true, error: null });
await firstValueFrom(service.remove(id));

Step 5 — The service builds the request

EmployeeService.remove() turns that into an actual HTTP request:

this.http.delete<void>(`/api/employees/${id}`)

Step 6 — Down through the five checkpoints

The request now travels through the interceptor chain, outermost first:

  DELETE /api/employees/7
        |
  1. profiling   starts a stopwatch
        |
  2. auth        attaches Authorization + X-Portal-Role: ADMIN
        |
  3. cache       not a GET, so it wipes the cached lists
        |
  4. error       stands ready to catch a failure
        |
  5. mock backend answers from memory instead of a real server

Each one is a small function that can inspect the request, change it, or answer it outright. The order is chosen deliberately: profiling wraps everything so it can time even a cache hit; auth runs before the cache so cached entries carry the right role; the mock backend is last so everything else behaves exactly as it would against a real server.

Step 7 — The fake backend decides

The mock backend reads the role header and enforces the real rule:

if (role !== 'ADMIN') {
  return forbidden(req.url, 'Only administrators may delete employee records.');
}
db.employees.splice(index, 1);
return noContent();   // 204
This is the real lock. Even if someone forced the hidden button to appear, the request would come back 403 Forbidden. That is the difference between hiding a button and enforcing a rule.

Step 8 — Back up through the checkpoints

The 204 response travels back up the same chain in reverse. The error interceptor sees no error and passes it through. The profiling interceptor stops its stopwatch and records the timing — which is what later appears on the admin System Health page.

Step 9 — The store updates its memory

patchState(store, (state) => ({
  employees: state.employees.filter((e) => e.id !== id),
  loading: false,
}));
notifications.success('Employee removed.');

Note filter: it builds a new array without that person rather than editing the old one. A new array is a new value, so the signal genuinely changed, so everything watching it is told.

Step 10 — Everything redraws itself

Because one signal changed, all of this happens with no further code:

  • the table row disappears;
  • the "Total employees" tile counts down — it reads a computed built on that same list;
  • the dashboard's department bar chart reshapes;
  • a green toast slides in at the corner;
  • the audit log on the admin page gains a line.
The whole point: nine of those ten steps are about data. Only the last one is about the screen, and it is automatic. This is what people mean by "reactive": you change the data, and the interface is simply a picture of the data, so the picture updates itself.
Worth noticing: the same journey happens for every action in the app — approving leave, publishing an announcement, creating a department. Component → store → service → interceptors → backend, and back. Once you have seen it once, every other feature is the same shape with different nouns.

5.5 core/interceptors — the HTTP checkpoints

Every HTTP request in this app passes through five functions on the way out, and every response comes back through the same five in reverse. Each is small and does exactly one job. 

  your code calls http.get('/api/employees')
        |
        v
  1. profiling      start stopwatch  ---------------------+
        |                                                 |
  2. auth           add token + role header               |  the response
        |                                                 |  travels back
  3. cache          fresh copy? answer instantly          |  up this side
        |                                                 |
  4. error          watch for failures                    |
        |                                                 |
  5. mock backend   answer from memory  ------------------+
Why this exact order? Profiling is first so its stopwatch wraps everything — including a cache hit, which never reaches the network. Auth is before cache so cached entries already carry the right role. Error sits closest to the transport so it sees failures in their raw form. The mock backend is last, standing exactly where a real server would — which means swapping in a real API is deleting one file.

list.push(item) on a signalupdate((l) => [...l, item]) — a new array, so the signal actually changes.
array.sort() on stored data[...array].sort() — sort a copy, because sort rearranges in place.
Forgetting params = params.set(...)Reassigns, because HttpParams is immutable.
A timer that never stopstakeUntil(destroy$) plus a real teardown function.
Calling a method from a templateA pure pipe or a computed, so it does not run on every check.
Trusting the browser for permissionsChecking the role again in the data layer.
Touching localStorage during SSRChecking isPlatformBrowser first.
innerHTML with user texttextContent via Renderer2, or Angular's sanitiser.

The five-sentence summary

If you remember nothing else:

1. A component is one piece of screen; the app is components inside components.
2. A signal is a value that announces its own changes, so the screen redraws itself and no code ever says "now update the display".
3. A store holds shared data in one place, so two screens can never disagree.
4. Every HTTP request passes through five interceptors that time it, sign it, cache it, catch its errors, and finally answer it.
5. Roles are checked three times — at the route, in the page, and in the data layer — and only the last one is a real lock.
